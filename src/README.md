# Building the site

`index.html` is assembled from the files in this folder.

## Site
- `site/*.js`, `site/app.css`, `site/shell.html`: the page. Each `.js` file is a slice of one script, joined in the order listed in `site/assemble.py`. `math.js` is the Math section; `home.js` is the Home page, the navigation (subjects, tabs, "On this page" line, footer), the Appearance menu and the Suggest page; `boot.js` is the router.
- `hub.js` is the Learn overview of each subject (`buildHub`, with `hubIndex` gathering every lesson, type, rule and term into one list to search) and the sample question on Home (`htryShow`). The section bar is in `home.js`: every page in `SUBJ` names its group, `renderSecnav` draws the four groups and `renderSubnav` the pages of the current one.
- `plan.js` is shared by both subjects: the starting check's estimate and its wording (`diagEstimate`, saved in `store.s.diag`), spaced repeats (`store.s.sr[subject][id] = [step, due]`, updated by `srNote` wherever an answer is saved), and the study plan (`#plan`; settings and today's tasks in `store.s.plan`). `PSUB` at the top is the one place that tells the plan how each subject stores results, lists its types and starts a set.
- `habit.js` and `data.js` are shared by both subjects. `habit.js` keeps the day log (`store.s.days['2026-11-12'] = [Math answers, Reading and Writing answers]`), the streak, the calendar and the question of the day; every place that saves an answer calls `noteAnswer(subject, id, ok)`, which schedules the repeat (`srNote`) and counts the day. `data.js` is the page at `#my-data`: what is saved, the backup file (`bkBody`), reading one (`bkParse` and `bkClean`, which keep only plain values, ordinary names and short plain strings; free text is allowed only in notes, suggestions and the "evidence" line, all of which are escaped where shown), adding it to what is here (`bkMerge`) and the offline controls (`offList` is every file a question needs that is not inside the page).
- `account.js` is the optional account (`#account`): signing in and out through a Supabase project's auth addresses with plain `fetch`, and the sync. `save()` in `core.js` calls `acctChanged()`, which sends the saved progress a moment later; `acctOnce` reads the account's row and sends, takes or joins (`bkMerge`), and every send names the row version it replaces. The project address and public key are in `build/account.json` (empty: accounts off, the site unchanged); the table is made by `account/setup.sql`. The session is kept under the `sat-sprint-account` key, apart from the progress, so it is never in a backup file. The project sends its emails (password resets) through Resend; Supabase's own email service writes only to the project's team, and `acctErr` says so plainly if that is ever what answers.
- `account/extras.sql` (run once in the Supabase SQL editor, after `setup.sql`; safe to run again) adds three things visitors can only add to, never read: `suggestions`, the messages from Ask or suggest (`home.js`: Send it posts the kind, the part of the site, the message and an optional name with the public key and no sign-in; a hidden box catches robots; 10 a day from one device; at most 30 from everyone in 10 minutes; when it cannot be saved, the message stays and Copy and GitHub are offered); `visits` with `count_visit`, a count per day and page (`visits.js`, called by `go()` in `boot.js`: no cookie and nothing kept in the browser, only on satsprint.org, never when the browser sends Do Not Track or Global Privacy Control; a question counts under its kind, `rq` or `mq`; "visit" counts page loads); and `ping()`, which `.github/workflows/keepalive.yml` asks every day so the Free project is never paused for inactivity (until the SQL is run it reads the progress table instead, which is refused but still reaches the database; a red run means the project did not answer). The end of `extras.sql` has the queries for reading messages and counts in the SQL editor.
- `.github/workflows/checks.yml` runs the checks on every push and pull request: "Build and data" (index.html must be a fresh build of `src/`, the script parses, each name declared at its top is declared once, theme contrast and generated CSS, the generated Math lists, the study pack, the drill cards, the R&W records, the link-preview tags), then the browser checks in three groups at once. A red run names the failing check in its log; nothing there deploys.
- Prizes (`prizes.js`, `fx.js`, `radiant.js`, `gems-weather.js`, `looks.js`, `crates.js`, `prizes.css`, `prize-themes.css`): coins and crates of looks for the site; nothing is ever locked and coins are never sold. `prizes.js` is the catalog (219 prizes: 209 in 19 series, Pencil Case, Varsity Locker, Night Shift, Arcade, Seasons, Deep Sea, Myth & Magic, Tech Lab, Haunted, The Unknown, Dreamscape, Zenith, Paradox, Rocks & Gems, Forecast, Wildlands, Curiosities, Dress-Up and Test Day, and 10 Radiant ones in none; six kinds: themes, right-answer effects, auras, paper, streak styles and character skins; six tiers, from Common 59.9% through Mythic 0.5% to Radiant 0.1%; a series' own prizes are 3 times as likely in its crate; the Seasons crate follows the school year (`PZ_SEASONS`: fall, winter, spring, summer by month), and a prize in season is 6 times as likely in it, twice the rest of the series, while every prize can still turn up and comes back next year) and the record in `store.s.pz`: `e` coins earned and `x` coins spent, one key per event (`qotd.m.<day>`, `plan.<day>`, `rev.<day>`, `crate.<id>`, `freeze.<id>`, `dupe.<id>`), `o` crates opened, `g` free crates, `fz` days a streak freeze covered, `st` stickers, `eq` what this device has on. The balance is earned minus spent and is never stored; `pzMerge` (called by `bkMerge`) joins two devices by the larger value or by union, so nothing is lost or counted twice. Keys use only the characters a backup may hold (`BK_KEY`). Coins are counted after every save (`pzSoon`, from `save()`): each subject's question of the day 10, every task on today's plan 20, 5 for each miss given a reason (4 a day). A note at the foot of the screen says what came in (`pzToast`; it never takes a tap and never shows in a timed module). The coin count sits in the top bar only where it fits without making the bar taller (`pzChip` asks again on resize, when the fonts arrive and when the text size changes); Home's streak box always shows it with the free crates waiting. Study luck (7 days in a row 1.5×, 30 days 2× on Legendary, Mythic and Radiant), an Epic or better within every 10 crates (that promise never brings a Radiant), 20 coins for a duplicate, a free welcome crate after the first day of practice, free crates at 7 days (Rare or better), 30 days (Epic or better) and 100 days (Mythic or better) and in the test-day week, and streak freezes (30 coins, used on their own when a missed day would end a streak; `habitStreak` counts a covered day). `fx.js` draws the looks: auras on Home's streak plate, the right-answer effects (`pzRight` from the answer cards in `core.js`, `reading.js`, `practice.js` and `math.js`), tier reveals, living themes and moving paper (Falling leaves, Snowfall and Blossoms are the Seasons backgrounds). Deep Sea, Myth & Magic and Tech Lab add the Jellyfish, Leviathan, Rune ring, Crystal bloom, Dragon coil and Radar auras; the Splash, Koi, Spell circle, Phoenix, Pixel pop, Glitch (cut slices of the answer, like Shatter) and Time freeze effects; the Bubbles, Kelp forest, Fireflies, Circuit board and Warp speed backgrounds; the Abyss, Enchanted and Terminal living themes; and the Dragon egg and Battery streak styles. `fxRune` and `fxJelly` are shared by several of them. Haunted, The Unknown and Dreamscape add 25 more (ghosts, bats, watching eyes, the Nightmare effect; slime, a portal, a saucer, The Watcher; butterflies, paper cranes, the Kitsune, lanterns and the Star whale), with `fxEye`, `fxGhost`, `fxBat` and `fxUfo` shared. Zenith and Paradox hold the stage auras (`FX_STG` in `fx.js`): a whole scene drawn in code above the streak, in a box 330 by 190 with the ground at y = 160 (a patterned floor, a centerpiece, things in orbit, rising particles, words that fade in and out), on a taller plate (`pz-plate-stage`). They are Polar veil, Spiral arm, Totality, Crescendo, Hearthwood, Seraph, Segfault, Overtime, Tesseract, Equilibrium and Monolith. The two series also hold scenes in the other kinds of look: the Spotlight, Starlit check, Curtain call, Liftoff, High tide, Epiphany and Dragonflight effects; the Paper planes, Rainy window, Clockwork and Low orbit backgrounds; the Metropolis and Summit living themes; and the Hourglass, Crown and Comet tail streak styles (the Crown gains a jewel each week, and each Comet tail drawing gets its own gradient id, because a copy inside a hidden page would leave the later copies unfilled). The Mythic reveal is a short scene of its own: an eight-pointed star turns and grows while three lines type out (the odds in the middle), a ring of runes pulses twice, and the prize shows at 4.5 seconds. Radiant, the tier above Mythic, is in `radiant.js`: the Beacon living theme; the Diamond ring, Fortissimo and Starforge effects; the Kintsugi, Orrery and Rose Window auras; the Gyre paper; the Learning tree streak style; and the Daybreak character skin (its arrival: a sunrise behind a small figure on a hilltop, a boy or a girl as the student's character is, drawn by `zHero`). They are in no series (`'any'`), so every crate holds each of them at the same chance, 1 in 10,000 (the tier's 0.1% shared by ten), and each plays its own arrival when won (`FX_REVEAL.z`, given the prize by `fxReveal`), with the card at 5.4 seconds. `zSub` draws a look on a small canvas of its own, so an arrival can place, grow and fade it. Rocks & Gems and Forecast are in `gems-weather.js`: 35 looks, seven of each kind, two Commons, two Rares, an Epic, a Legendary and a Mythic, among them the Supercell stage aura, the Black opal, Thunderhead and Crystal cavern living themes, the still Terrazzo pattern (`html.pz-p-terrazzo`) and seven streak styles that change at 7, 30 and 100 days. Wildlands and Curiosities are in `looks.js`, 25 scenes across every kind and tier, built to the standard of the Radiant looks: the Campfire, Fortune teller, Mimic, Caldera and Kilonova stage auras (added to `FX_STG` and wrapped by `fxStageWrap`); the Dominoes, Jackpot, Murmuration, Anglerfish and Threshold effects, which clip the answer's box out of everything they draw (`lkOut`), so nothing ever covers the answer, and end on a frame and a sheen (`lkFinish`); the Honeycomb, Meadow, Hot-air balloons, Ink wash and Wanderers backgrounds; the Halcyon and Lily pond living themes (light) and the Mycelium, Dunes and Thin ice ones (dark); and the Tally marks, Paper chain, Marquee, Lotus and Ouroboros streak styles (in `FX_STREAK`). They add themselves to the registries in `fx.js` (streak styles through `FX_STREAK`, which `fxStreakIcon` asks first) and share `gwGem`, `gwPrism`, `gwCloud` and `gwStage`. `gwLit` adds light on a dark page but paints it on a light one, because adding light over a dimmed light page makes it darker. Every canvas runs only on screen, never inside a timed module (`.mmwrap`), and holds still for reduced motion. `crates.js` is the Crates page (`#crates`). The owner's link, `#gift-<code>`, gives every prize, sticker and title and 10,000 coins (`pzGiftAll`), saved under `gift.*` like a crate's prizes so it reaches every device on the same account; opening it twice adds nothing. The page holds only the SHA-256 of the code (`PZ_GIFT` in `prizes.js`), and `pzGiftLink` takes the code out of the address bar and history before the router reads it. To retire the link, put the SHA-256 of a new code in `PZ_GIFT`; what was already given stays. The prize themes are `PRIZE` in `src/tools/themes.py`, checked with the others; `python3 -I src/tools/themes.py --prizes src/site/prize-themes.css` writes their CSS, and `python3 -I src/tools/themes.py --fxpal src/site/fx.js` writes their colors into `fx.js` (`FX_PAL`, for swatches and previews); the Checks workflow fails if either is out of date.
- `challenge.js` is **Challenge a friend** (`#challenge`, `#challenge-m`, `#challenge-rw`), and needs no server. A student picks a subject, a topic (one of the four areas) and a level, and gets five questions (`chalPick`: ones not tried yet first; a mix is two easy, two medium and one hard; easier first), answered on the ordinary practice screens (`chalPlay` gives the Math set or the Reading and Writing set its challenge: `MP.chal`, `TS.chal`). The results page then makes the link (`chalEndHTML`, called from `mpSummary` and `timedFinish`): `#ch-<m|rw>-<score>-<question ids, 3 to 10>[-<name>]`, sent through the phone's share sheet when there is one, or copied. A friend's link (`chalOpen`) says who sent it and the score to beat, plays the same questions in the same order, and then shows both scores, who won, and a link of the same kind to send their score back. Only a first try that answers every question counts; a second try says so and leaves it. An ordinary set of 3 to 10 questions offers the same (`chalOfferHTML`). Each device keeps the last 20 challenges in `store.s.chal` (keyed by subject and a hash of the questions: the first score, the latest try, the scores friends sent, and whether it made it) and the name it signs with in `store.s.chn`; names keep only letters, digits, spaces, dots and dashes, at most 20, and `bkMerge` joins two devices with `chalMerge`. Answers count as ordinary practice and earn no coins of their own. The visit counter counts every challenge link as `ch`, with nothing from the link.
- `room.js` and `room.css` are **My room** (`#room`), the first part of the clubhouse: a drawn room where a student puts the prizes they own on show. Nine spots can change: the walls (Classic or a prize theme; a living theme also fills the window with its scene), the window (the sky, or a paper as the view), three stands (an aura or a right-answer effect on each), the shelf (three streak styles), the sticker board (six stickers found in crates), the name plate (the name in `store.s.chn`, the same one challenges sign with, and an earned title) and the student, their character (`buddy.js`): a boy or a girl, five skin tones, six hair colors, and either one of eight colors with one of six hats or a character skin they own; the desk shows the streak and does not change. Until the student saves, the room is made from what they have on and then their rarest prizes (`roomStart`). Decorate works on a copy (`ROOM.draft`) and Cancel drops it; Save writes `store.s.room` = `{ v: 1, t: <time saved>, w: <theme>, win: <paper>, st: [3 prize ids], sh: [streak styles], bd: [stickers], tl: <title>, av: [color, hat, skin, 'b' or 'g', tone, hair] }`. Wearing a skin from the Crates page, before any room is saved, writes `{ v: 1, t, a: 1, av }`: only the character, the rest of the room still made as if unsaved (`roomWear`, `roomGet`). Every saved room is read through `roomClean`, so it never shows a prize the student does not own, a title not earned, a sticker not found, or anything not on its lists, and `bkMerge` keeps the room saved last (`roomMerge`). The room is drawn from that record and the prize catalog alone (`roomRoomHTML`), so a shared room is drawn the same way for its visitors (`club.js`); signed in to an account in the clubhouse, each save is also sent to the account (`club_room_save`). Tapping a spot shows its card (with the crate and the odds) and plays an effect; "Everything in my room" says it all in words. On phones the room stays at the top of the screen while decorating. Its names all begin with `room` or `ROOM`, because every file shares one set of names and `rm` belongs to `rw-module.js` (`src/check/names.js` fails on a name declared twice).
- `buddy.js`, `pal.js` and `buddy.css` are the student's **character** and the **study buddy**. `buddy.js` draws the character as an SVG, chibi style (`budSVG(look, o)`: a big head on a small body, in layers: aura, back, hair, legs, body, arms, head, face, hat or the skin's own top, front and fore), with a skin's own palette, parts and effects (`BUD_SKINS`: 16, from Sleepyhead to Daybreak, the Dress-Up series plus the Radiant one), its faces and mouths (`BUD_FACES`, `BUD_MOUTHS`), and its moves (`BUD_ACTS`, played by `budPlay` with a `data-act` on the SVG and CSS keyframes in `buddy.css`). Each skin has a personality (`budWho`): its mood line, the moves and lines for a tap, its idle moves, and what it does on a right answer and on a miss. The same drawing is the figure in My room, in a friend's room and in live rooms (where it walks and hops), the prize pictures and reveals in Crates, and the study buddy. `pal.js` is the **study buddy**: the student's character, small, on every page; beside the page bottom left on a wide screen, and on a narrow one only its head peeking up in the bottom right corner (behind the bottom bar on a phone), with room added at the foot of the page (`body.pal-pad`) so the end of every page can scroll clear of it. A tap plays one of its skin's moves and a line, with a Hide me button in the bubble (the × shows only to a mouse or a keyboard); now and then it moves on its own; it cheers a right answer (`pzRight` calls `palSaw`) and shrugs off a miss (`noteAnswer`), walks in on a new page, falls asleep after 3 minutes alone, and says hello the first time (`sat-sprint-buddy-hi`). It is never in a timed module, My room, a visit, the tour or the calculator, and a crate opening covers it. Hide puts it away until the tab closes (`sessionStorage` `sat-sprint-buddy-hide`); Text size and colors has a switch that turns it off on the device (`localStorage` `sat-sprint-buddy`). With reduced motion it stands still. Its names begin with `bud`, `BUD`, `pal` or `PAL`.
- `account/club.sql` is the clubhouse's server part (run once in the Supabase SQL editor, after `setup.sql` and `extras.sql`; safe to run again): nicknames, coins, crates, prizes, stickers and free crates kept on the account, rooms with share links that can be switched off, and stickers visitors leave on a shared room's board. Its tables (`club_*`) cannot be read or written from a page; the page calls its functions (`club_join`, `club_state`, `club_claim`, `club_open`, `club_freeze`, `club_gift`, `club_nick`, `club_room_save`, `club_room_link`, `club_room_view`, `club_board_add`, `club_board_remove`, `club_erase`), and each checks who is asking and gives no more than the page would: the same draw as `pzOpen` (odds, luck from the server's own streak, the promise of an Epic, a series' own prizes 3 times as likely, the Seasons prizes in season 6 times), the same free crates and freezes, and coins only for the day's reasons (two days ago to tomorrow, Eastern time), at most 60 a day. Joining copies the device's record once (`club_join`), checked the way the page makes it, so a changed record brings no more than honest practice could have: days from the site's first day, coins for days since crates came (15 November 2026), crates only while those coins pay for them, oldest first, free crates only when the days or stickers carried earn them, each sticker from its crate; the owner's link is not carried (opening it again signed in calls `club_gift`, which checks the code against the hash in the prize list). A room keeps only what its owner holds on the server (`club_room_clean`; a character skin too, and a figure's tone and hair only in the form the page uses), and a link is 32 random hex digits, new each time sharing is switched on. The prize list is not copied by hand: `make_index.py` writes `catalog.json` beside `index.html` (`site/catalog.py` reads `prizes.js`: each prize's id, tier and series, and the odds, prices, seasons, sticker pages, titles and gift hash), and the database asks satsprint.org for it every 10 minutes (`pg_net`, `pg_cron`), so a new prize is in within 20 minutes of reaching the site, and a list in a shape the draw does not expect is refused and noted (`select note from public.club_rules`). The end of `club.sql` has the queries for the site's owner (mark the owner's account, rename or block someone, take a sticker off a board).
- `club.js` is the clubhouse on the page. Signed in to an account whose project has `club.sql`, a student's coins, crates, prizes, stickers, free crates and streak freezes are the server's: `pz()` returns its record (`CLUB.P`, in the shape of `store.s.pz`) and the page only asks: for the day's coins and practiced days (`club_claim`, from what `pzTick` would have counted: today's questions of the day, plan and reasons, and the days practiced today and the two before), to open a crate (`club_open`), to buy a freeze (`club_freeze`), and to take the owner's link (`club_gift`), one call at a time (`CLUB.line`), so an answer about the record from before a crate or the owner's link never lands after it. What the student has on (`store.s.pz.eq`) stays in the saved progress. The first sign-in carries the device's record over (`club_join`), once per account: prizes won later on a guest device are not added when that device signs in, only its last three days of coins and practice (by the claims). The server's last answer is kept on the device under `sat-sprint-club` (`{ uid, st, pend }`), so a page opens with it, and opens nothing while the server cannot be reached; `store.s.club = 1`, in the saved progress, tells a device that has not heard from the server yet that the account is in the clubhouse, so it earns and opens nothing meanwhile (`clubWait`). Erase my progress everywhere empties the account's record too (`club_erase`; the next sync joins again with nothing), deleting the account leaves the device the prizes it was showing, and signing out removes what was kept. A project without `club.sql` answers 404 (`PGRST202`) and the page keeps prizes on the device as before. **Share my room**, under the room (`clubShareHTML`): a nickname first (3 to 20 letters or digits, with spaces, dots or dashes between; no one else's; not 7 digits or more; no word from `club_words`), then a link (`club_room_link`), Copy or Send, Stop sharing, and the stickers visitors left, each with Take it off. `#r-<link>` (`clubVisit`, the `visit` view) shows anyone the room, the owner's nickname and streak, and the board; a signed-in visitor can leave one of their own stickers there, one a day per room. Its names begin with `club` or `CLUB`.
- `account/club-live.sql` is the clubhouse's second server part, **live rooms** (run once in the Supabase SQL editor after `club.sql`; safe to run again), and then Realtime > Settings > "Allow public access to channels" is switched off, so that a page can only listen to a channel the policy allows and cannot send on one. A signed-in student with a nickname who opens a shared room's link can join it live (`club_live_join`): up to 8 in a room and 20 across the site (`club_live_config`). The server keeps them a place (`club_live_leases`) while their page pings every 30 seconds (`club_live_ping`; 75 seconds without one, or 6 minutes without doing anything, ends it) and answers who is there: each one's id in that room (`left(md5(salt || user id), 10)`, never the account's id), nickname, the color and hat of their own room and their whole character (a skin too), and where they stand. Each room has a private Realtime topic, and the policy on `realtime.messages` lets only the students with a place in it listen (`club_live_can_listen`); since Realtime checks it when a page starts listening, asking someone to leave moves the room to a new topic. Pages never send on the channel: a move, a reaction (six) or a phrase (ten, from `club_live_words`; nobody types) goes through `club_live_say`, which checks it (one move every 2 seconds, one reaction or phrase every 3, 400 actions a student a day), counts it, and sends it with `realtime.send`. A message counts once plus once for each page in the room, as Supabase counts them, and after 1,000,000 in any 30 days (the Free plan allows 2 million a month) live rooms rest until the count falls; saved rooms still show. Block (`club_live_block`) keeps two students out of each other's rooms and hides them from each other in any room; report (`club_live_report`, 10 a day) keeps the nicknames, the reason and the last 30 minutes of what was done in the room (`club_reports`); a room's owner can ask someone to leave until tomorrow (`club_live_remove`). Stopping sharing, the site's owner blocking someone, erasing a clubhouse record, deleting an account and switching live rooms off (`live_on`) end live visits at once (triggers on `club_rooms`, `club_profiles` and `club_live_config`). `club_live_count` tells a room's page, signed in or not, how many are live in it. The end of `club-live.sql` has the owner's queries: who is live, reports (and marking one dealt with), messages used, switching live rooms off, and the blocks students made.
- `live.js` is live rooms on the page, in the shared room's view (`#r-`, after the room and before the stickers; club.js calls `liveEnter`, `liveDraw` and `liveAway`). Join live, then: each student is a figure on the room's floor (`liveFloor`; the owner's still figure steps aside while the owner is live), a tap in the room walks there (a key on a spot walks to the front of it), reactions float up and phrases show in a bubble, and "Here now" lists everyone with Options (mute on this screen, report, block, and for the owner Ask to leave), plus People you blocked. The page talks to Realtime itself (`liveSock`, a small Phoenix 1.0.0 client: join the room's private topic with the student's sign-in, a heartbeat every 25 seconds, a fresh sign-in when it changes) and only listens. Who is there comes only from the server, so a message from anyone not on the list is ignored, and an answer asked for before word that someone left (or moved) cannot bring them back. A screen reader hears who came in, who left, and what was said (`.live-news`). The page leaves when the student presses Leave, opens another page, closes the tab (a keepalive request), keeps the tab hidden for a minute (and comes back when it is shown), or does nothing for 5 minutes. Without `club-live.sql` (404, `PGRST202`) a shared room shows with no live part. Its names begin with `live` or `LIVE`.
- `sw.js` (at the site root, beside `index.html`) is the service worker: the page is fetched from the network first and from its saved copy when there is none, so a new build needs no change there; question files and pictures are answered from the saved copy and refreshed in the background; Google Fonts are kept too. Math question files and the symbol library are asked for with a stamp (`?v=…`, see Questions as text): a stamped file never changes, so it is not refreshed, and keeping one drops the copies of that file kept under older stamps. Rename a cache only if those rules change (v2 dropped the v1 rule that kept `m/t/_glyphs.js` from the first visit for good; `data.js` names the question cache too, as `PWA_Q`). `manifest.webmanifest` and `icons/` make the site installable; `python3 -I src/tools/icons.py icons` redraws the icons (needs Pillow). The `<head>` lines for both are in `site/make_index.py`, with the link-preview tags (Open Graph): `icons/og.png` is the 1200 × 630 picture a shared satsprint.org link shows, and `node src/tools/og.js icons/og.png` redraws it (needs Playwright). `python3 -I src/check/head.py index.html` checks those tags and the picture.
- `module-core.js` is the timed-module engine both subjects share: the clock, movement between questions, marks for review, the list of every question and the check before finishing. `rw-module.js` is the Reading and Writing module (it draws the ordinary question cards and stops a click from revealing the answer); `rw-track.js` gives every Reading and Writing question a type (a reading set or a grammar rule) and draws that subject's map (`#rw-map`) and trap report from the practice records in `store.t`, `store.r` and `store.b`. Module scores are in `store.s.rwmodules`.
- `math-track.js` is the mastery map (`#m-map`), the "What went wrong?" prompt and the trap report; `math-module.js` is the timed module and the calculator panel; `msheet.js` is the reference sheet (`MSHEET`: each figure as inline SVG with its formulas as text), its Reference button and panel, which shares the calculator panel's place on the screen (one open at a time). Both read the last attempt per question from `store.m`; reasons for misses are in `store.x`, and module scores in `store.s.modules`.
- Colors: every color is a token (`--paper`, `--ink`, `--act`, `--rw`, `--math`, …) set once per theme at the top of `app.css`. `python3 -I src/tools/themes.py src/site/app.css` rewrites that block from the palettes in `themes.py`; it first checks every text/background pair the page uses (and white text on each gradient stop) and stops without writing if one is below 4.5:1 contrast. The chosen theme is saved under the `sat-sprint-theme` key; with none saved the page follows the device's light or dark setting.
- `vocab.js` is **Words to know** (`#vocab`): the word list for Words in Context, the positive-or-negative check, second meanings and the purpose words in Purpose and structure choices. `python3 -I src/reading/vocab.py` writes `build/vocab.json`; it counts everything from `build/bank.json`, and the definitions (`vocab_defs.py`), second meanings (`vocab_second.py`) and purpose words (`vocab_func.py`) are written for this site.

## Math data and images
Made from College Board's SAT Math question bank export (`questionbank-export-2026-10-8.pdf`, 2,030 pages, 1,925 questions; not included). Run the scripts in `src/math/` from one working folder that holds the PDF text, in this order:

1. `pdftotext -layout bank.pdf math.txt` then `mparse.py`: labels, stems, answers and explanation text per question (`math.json`).
2. `pdftotext -bbox-layout bank.pdf mbbox.html` then `mgeo.py`: where each question's Question / Answer / Correct Answer / Rationale headings sit (`mgeo.json`).
3. `pdftoppm -r 130 -gray -png bank.pdf pg/p`, then `mcrop.py`: crops each question (stem and choices) and its explanation into `mimg/q` and `mimg/r`.
4. `mreflow.py`: cuts each image into lines and words and re-wraps them into a 380-pixel column for phones (`mimg/qn`, `mimg/rn`).
5. `mbuild.py` writes `mdata.json`. It uses `mclass.py` (question types), `mcontent.py` (lessons and type cards), `mpatterns.py` (the rules that tag each question with the big patterns, and the rare patterns), `mpatcontent.py` (pattern cards, the Desmos playbook, the Desmos line for every type) and `verified.json`.

## Questions as text
`src/text/` rebuilds questions from College Board's PDF exports (not included). It needs PyMuPDF and Pillow.

```
python3 -I src/text/build_math.py math-export.pdf m/t --report=/tmp/report.json    # m/t/<id>.js, m/t/_glyphs.js, src/build/mtext.json
python3 -I src/text/build_rw.py rw-export.pdf            # report only
python3 -I src/text/build_rw.py rw-export.pdf --write    # rewrites figures.json and grammar-sources.json, crops into rw/f/
```

- `qbx.py` reads one question's pages: text spans from the text layer, every drawn path and placed picture. It finds the headings, groups strokes, boxes and rules into figures (with their labels), sets the remaining symbols on the line of text they are level with, and returns paragraphs, display equations and figures in reading order, plus `audit()` warnings.
- `render.py` writes HTML: text as text, a group of symbols as an inline SVG sized in em and placed on the baseline, older picture-formulas as inline images, figures as WebP crops. Each distinct symbol outline is stored once at one size and placed with `<use>`.
- Some older questions set an exponent or a subscript as smaller text, raised or lowered a few points (x², 10⁸, x₁). `attach_scripts()` in `qbx.py` gives each such run the baseline of the word it touches and marks it, and `render.py` prints it as `<sup>` or `<sub>`; a run with nothing beside it is reported by `audit()`, which holds the question back. Before this, the raised digits were read as a line of their own and printed apart ("2 2 2" before the sentence).
- `build_math.py` runs every Math question in parallel, merges the symbol library (outlines that agree within two units in a box of 100 are one symbol), checks each answer against the key in `mdata.json`, and writes only the questions that pass. `build_rw.py` does the same for the Reading and Writing questions that were pictures, splitting the rationale by choice. Both can be rerun; a rerun starts from the same state as a first run.
- On the site, `math-text.js` loads a question's file when it comes near the screen and replaces the placeholder; `mImg()` in `math.js` returns the placeholder or, for a held-back question, the picture (`mPic()`).
- The symbols get short names (`G0`, `G1a`, …) in the order they are first met, so a rebuild that adds questions names them afresh, and a question must never be drawn with the library of another rebuild (π came out as d, % as g). `assemble.py` stamps the page with a hash of every file in `m/t` (`D.mathText.v`), and `mtxUrl()` asks for each file with that stamp, so a device fetches the matching set after every rebuild. Rebuild `index.html` after any change to `m/t`.
